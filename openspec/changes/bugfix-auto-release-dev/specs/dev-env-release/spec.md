# Spec Delta

## Purpose

把缺陷修复发布到开发环境（app-test）的交付能力：在保证不动演示环境、不与其他 agent 并发冲突、不遗漏跟踪分支代码的前提下，把本次改动的应用发布到开发环境，并证明环境的实际产物与本地构建一致。

## ADDED Requirements

### Requirement: 环境隔离

发版目标 MUST 只能是开发环境。任何指向演示环境的目标地址 MUST 被拒绝，且拒绝发生在任何构建或网络写入之前。

#### Scenario: 显式指定开发环境

- **WHEN** 操作者以开发环境地址 `http://192.168.181.104:30669` 调用发版
- **THEN** 发版继续执行
- **AND** 全程不向演示环境 `http://192.168.181.104:30680` 发出任何写请求

#### Scenario: 误传演示环境地址

- **WHEN** 目标地址不含 `30669`（例如被误传为演示环境的 `30680`）
- **THEN** 发版立即以非零退出码终止
- **AND** 不执行构建、不上传、不上架、不更新任何应用

### Requirement: 跨 agent 互斥

同一环境在同一时刻 MUST 只允许一个发版在跑。互斥范围 MUST 覆盖所有工作区，而不是单个工作区。

#### Scenario: 两个工作区同时发版

- **WHEN** 工作区 A 正在向开发环境发版，工作区 B 也开始向同一环境发版
- **THEN** 工作区 B 在开始构建前就失败退出
- **AND** 退出的提示说明"已有发版在进行"，而不是静默等待或静默跳过

#### Scenario: 发版结束后释放

- **WHEN** 工作区 A 的发版正常结束或因错误中止
- **THEN** 锁被释放
- **AND** 后续发版可以正常获得锁

### Requirement: 发版前合并跟踪分支

发版使用的代码 MUST 包含跟踪分支的全部内容。若本次修复所在分支落后于该仓库的跟踪分支，发版前 MUST 先把跟踪分支合并进来。

#### Scenario: 修复分支落后于跟踪分支

- **WHEN** 修复分支缺少跟踪分支上的若干提交
- **THEN** 发版前把跟踪分支合并进修复分支
- **AND** 合并后的分支被推送，使评审看到的分支与发版所用代码一致

#### Scenario: 合并产生冲突

- **WHEN** 跟踪分支与修复分支存在冲突
- **THEN** 发版中止，不产出任何包
- **AND** 报告冲突文件，由 agent 解决后重试

### Requirement: 只发受影响的 应用

发版目标 MUST 由代码改动推导，而不是无条件全量发布。推导依据 MUST 是本次修复分支相对跟踪分支的差异文件。

#### Scenario: 改动集中在单个前端应用

- **WHEN** 差异只涉及某一个前端应用的目录
- **THEN** 发版只包含该前端应用
- **AND** 不构建、不上传其他应用

#### Scenario: 差异落在无法发布的应用

- **WHEN** 差异涉及该环境没有市场行的应用，或不具备构建前提的应用（如缺少对应 JDK 版本的模块）
- **THEN** 该应用被排除并在结果中明确说明原因
- **AND** 其余应用照常发版

#### Scenario: 没有可发布的改动

- **WHEN** 差异为空，或推导结果为空
- **THEN** 发版不执行上传与上架
- **AND** 明确报告"无可发布应用"，而不是静默成功

### Requirement: 发布后一致性校验

发版完成后 MUST 核对环境中的实际产物与本次构建产物是否一致，判据 MUST 同时包含版本与内容摘要（md5），不得仅凭接口返回成功就判定发布完成。

#### Scenario: 校验通过

- **WHEN** 发版完成后回读每个目标应用的市场行与已安装行
- **THEN** 两处的版本与 md5 均与本地构建产物一致
- **AND** 发版以成功状态结束

#### Scenario: 校验不通过

- **WHEN** 回读发现版本或 md5 与产物不符，或已被外部改写
- **THEN** 发版以非零退出码结束
- **AND** 逐条列出不一致的应用及两端的实际值

### Requirement: 与缺陷解决动作的先后顺序

发版 MUST 在把缺陷标记为已解决之前完成。标记已解决之后 MUST NOT 再尝试发版。

#### Scenario: 发版成功

- **WHEN** 发版与一致性校验均通过
- **THEN** 才把缺陷标记为已解决
- **AND** 解决说明中包含发版到的环境与验证结论

#### Scenario: 发版失败

- **WHEN** 发版或校验任一步失败
- **THEN** 缺陷不被标记为已解决
- **AND** 只追加一条说明失败原因与日志位置的备注，交人工判断

#### Scenario: 先标记已解决

- **WHEN** 缺陷已被标记为已解决
- **THEN** 该缺陷不再属于进行中状态，agent 会被停止
- **AND** 此时若仍在构建，构建过程会被中断，不会产出可用的发布
